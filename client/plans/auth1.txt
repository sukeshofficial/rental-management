# TASK: Redesign Reusable Rental Management Authentication UI Components

## 1. Objective

Redesign the existing Login and Registration UI components for our Rental Management application using the attached visual references and the existing `frontend-skill.md`.

The references establish the intended visual direction:
- Dark, premium, cinematic styling inspired by the supplied authentication designs.
- An equivalent polished light theme.
- A split-screen composition with a rental-property visual panel and an authentication form area.
- Consistent typography, refined input fields, clear hierarchy, restrained borders, and prominent primary actions.
- Purple/blue accent styling where appropriate to the supplied visual references.

The original Excalidraw mockup defines the required authentication fields and actions. Do not import additional features from the reference product.

**Primary objective: Build modular, reusable React JSX components that can be integrated into authentication layouts and reused on other pages through well-designed props.**

Do not treat this as a one-off screenshot recreation. The implementation must follow a coherent design system and the existing frontend architecture.

## 2. Mandatory rules before implementation

### A. Inspect the existing project first

Inspect the frontend source code before making changes.

Review:
- `frontend/package.json`
- `frontend/src/components/ui/`
- Existing Login and Registration components, if present
- Existing `ComponentTestBed`
- Existing shadcn/ui primitives
- Global styles, CSS variables, Tailwind configuration, and theme implementation
- Existing font imports, typography conventions, spacing tokens, radii, shadows, and colors
- Existing routes and application structure
- Available images and other local assets

Identify which components already exist and determine how they are currently used.

Existing components include or may include:

- `BrandTitle`
- `HomeButton`
- `AuthField`
- `AuthSubmitButton`
- `AuthLink`
- `PasswordStrengthIndicator`

Reuse these components when they already meet the requirement. Extend their props or styling only when necessary. Do not create duplicate versions of components that already provide the required functionality.

### B. Follow the existing design system first

The existing project is the primary source of truth for implementation conventions.

Inspect the established typography, spacing, shape, color, input, button, and theme patterns before deciding what needs to change.

Apply the supplied references as the visual direction for this explicit redesign. If that direction requires changes to the current design system, introduce them deliberately through shared tokens and reusable component variants rather than scattered, page-specific styling.

Do not introduce a new font, unrelated visual style, or competing theme mechanism without a clear reason.

### C. Preserve the technology stack

- Use React with JavaScript and JSX.
- Use `.jsx` for new custom React components.
- Do not introduce TypeScript, `.tsx`, interfaces, or TypeScript annotations.
- Reuse the existing shadcn/ui primitives and utilities.
- Preserve existing imports, path aliases, routing, and project conventions.
- Do not install new libraries unless existing project capabilities cannot satisfy a genuine requirement.
- Do not replace or reinitialize the existing frontend application.

Before installing anything, determine which dependencies and primitives are already available.

## 5. Implement both light and dark themes

Both themes must be deliberately designed and usable.

Do not treat light mode as a simple inversion of dark mode.

### Dark theme

Follow the supplied dark references:
- Deep charcoal or near-black backgrounds.
- Subtle separation between the main surface and form surface.
- High-contrast primary text.
- Muted but readable secondary text.
- Deliberate purple/blue accent treatment.
- Subtle borders and restrained depth.
- Visible input and keyboard-focus boundaries.

Avoid excessive glow, pure-black surfaces everywhere, or low-contrast labels.

### Light theme

Create the corresponding light variant:
- Light neutral backgrounds.
- White or appropriately elevated form surfaces.
- Dark, readable primary text.
- Clear secondary text and labels.
- Consistent purple/blue accents.
- Neutral input borders and clear focus rings.
- Subtle surface separation without unnecessary shadows.

The light theme should preserve the same overall visual identity as the dark theme.

### Theme implementation

Use the existing theme provider, CSS variables, and semantic tokens if available.

Reuse or establish appropriate tokens for:
- `background`
- `foreground`
- `surface`
- `surface-muted`
- `primary`
- `primary-foreground`
- `muted-foreground`
- `border`
- `input`
- `ring`
- Relevant error and success states

Keep shared component styling theme-aware. Do not hardcode a dark-only background or text color into a component that is intended to support both modes.

If the project already has a theme switcher, preserve and reuse it. Do not create a competing theme system.

If the theme mechanism supports runtime switching, all applicable components must update without requiring duplicated light and dark implementations.

Do not add a theme toggle unless it belongs in the existing application or the task explicitly requires one.

## 6. Build modular components with reusable props

Inspect the existing components before creating anything new.

### Existing shared components to reuse or refine

**`BrandTitle`**
- Configurable brand text.
- Optional link destination.
- Optional styling override.
- Consistent theme-aware typography.

**`HomeButton`**
- Configurable label and optional navigation destination.
- Click callback where appropriate.
- Disabled state and styling override.
- Consistent theme-aware button appearance.

**`AuthField`**
- Configurable `id`, `name`, `label`, `type`, `placeholder`, `layout`, `value`, `defaultValue`, and `onChange`.
- Support for appropriate native HTML input attributes.
- Required and disabled states.
- Validation error and accessible error description.
- Optional leading icon and trailing adornment if required by the reference.
- Optional password visibility behavior if this responsibility fits the component API.
- Shared typography, sizing, focus, border, and spacing conventions.

Support horizontal and stacked label arrangements if the existing use cases require them.

**`AuthSubmitButton`**
- Configurable `label`, `type`, `onClick`, `disabled`, and `loading`.
- Optional loading label and styling override.
- Consistent primary action styling.
- Correct native button semantics.

Use SIGN IN for Login and the configurable registration label for Registration.

**`AuthLink`**
- Configurable label and destination.
- Optional callback when appropriate.
- Correct semantic link behavior.
- Consistent link styling, focus, and hover states.

**`PasswordStrengthIndicator`**
- A configurable strength state such as `empty`, `weak`, `medium`, or `strong`.
- Optional visible strength label.
- Appropriate visual changes driven by props.
- Consistent theme-aware styling.

Do not create separate custom versions of these components for each authentication page.

### Additional components, only when justified

Create new shared components only if they represent a genuinely reusable responsibility missing from the existing component library.

Possible examples:

- `AuthBrandPanel`: reusable promotional panel with configurable headline, description, brand content, and optional existing image asset.
- `AuthFormHeader`: configurable heading and subtitle.
- A small password-visibility control if it cannot reasonably be handled by the existing `AuthField`.

Do not create trivial wrappers simply to increase the number of components.

### Prop API rules

Every new or modified custom component must follow these rules:

1. Use ordinary JavaScript props and JSX.
2. Give props meaningful, predictable names.
3. Provide sensible defaults where appropriate.
4. Use named variants and sizes instead of hardcoding visual differences.
5. Preserve native HTML behavior and accessibility.
6. Accept `className` or another intentional styling extension point where useful.
7. Keep component-specific business logic out of purely presentational components.
8. Avoid hidden state that conflicts with parent-controlled props.
9. Do not expose unnecessary props that undermine design consistency.
10. Reuse the same component API wherever the same UI responsibility appears.

A caller should be able to customize the label, field type, validation state, or CTA text without modifying the component implementation.

Components should look consistent by default because they consume shared tokens—not because every page manually passes a different set of styling classes.

## 8. Responsive behavior

The split-screen reference is primarily a desktop composition. Adapt it deliberately for narrower screens.

### Desktop
- Preserve the side-by-side brand and authentication regions.
- Prevent the form from becoming excessively wide.
- Maintain consistent margins and whitespace.
- Keep the primary action and account links easy to locate.

### Tablet
- Rebalance the panel proportions when needed.
- Prevent form fields from becoming cramped.
- Reduce promotional content density if necessary while keeping the essential form usable.

### Mobile
- Reflow the authentication experience into a usable single-column structure.
- Preserve the brand identity and form hierarchy.
- Keep all required fields and account links available.
- Prevent horizontal overflow.
- Ensure the keyboard does not obscure the active field or important actions.
- Make password controls and other interactive elements usable by touch.

Use the project's established responsive conventions and test representative narrow, intermediate, and desktop viewports when browser tools are available.

Do not claim responsiveness has been verified unless the relevant rendered layouts have actually been inspected.
